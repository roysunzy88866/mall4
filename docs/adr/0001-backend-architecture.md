# ADR-0001 · 后端务实分层架构

- **状态**:已采纳(2026-06-03)
- **决策者**:用户(AskUserQuestion 拍板)

## 背景
旧项目 CLAUDE.md 继承了「5 层后端 / 5 层车机」架构。商店4 重启时把架构从 CLAUDE.md 撤下,约定等后端需求定稿后重新评估。后端需求 2026-06-03 定稿:约 5 张表 + 简单 CRUD + 一条下单闭环 + 几条真业务规则。

## 决策
后端采用**务实分层**:接口层(views)→ 业务层(services)→ 数据层(repositories)→ 数据表(models),外加**业务规则(rules,纯函数)单拎重点测**。不强上完整 5 层(domain 不单列成重层),也不退回「Flask 路由里直接写」。车机端沿用 `ui → viewmodel → repository → api`。

## 理由
- 这是会迭代、要交接、用户看不懂代码的真项目 → 需要分层与可测性(契合用户选的「重纪律」)。
- 但只有约 5 张表,完整 5 层偏重、拖慢交付。
- 真正的业务风险集中在几条规则(推荐位 3~5、整单/价格快照、Banner 文案自动套、停用分类过滤、为你推荐排序)→ 做成纯函数单拎、100% 覆盖,性价比最高。

## 备选(未采纳)
- **全套 5 层**:最规整、最好交接,但对 ~5 张表的 demo 偏重、写得慢。
- **不分层**:最快,但业务规则散落、难测,违背「重纪律」。

## 影响
- [docs/architecture.md](../architecture.md) 按此落。
- CLAUDE.md 恢复「架构相关代码硬规矩」的务实版。
- 各项后端关键决策(D1~D9)记录在 [后端需求.md §9](../../后端需求.md),不在此重抄。
