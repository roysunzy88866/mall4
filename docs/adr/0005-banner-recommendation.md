# ADR-0005 · 推荐位编辑规则

- **Status**: Accepted
- **Date**: 2026-05-30
- **Tags**: backend, process, governance

## 背景 Context

C5 切片(US-ADMIN-05 推荐位编辑)开工时,发现共识对推荐位有三处互相打架的描述,而它们同指**一批数据**(ADR-0004 已明确:推荐位 = 车机端顶部那批幻灯,后台从全部商品里挑):

- 共识 §1 后台:「从所有商品里挑 **3–5 个**」
- 锚点 **F4a**:幻灯「**4 张**」
- 车机端 US-CAR-01 场景:容忍「**0 张**(空态不崩)」「**1 张**(不轮播)」

数量究竟是 4、是 3–5、还是允许 0–1,三者无法同时成立,写验收前必须裁定。另外共识写「可**拖拽**排序」,而 C3 分类管理已降级为「上移/下移」按钮(避免引前端拖拽库)。

## 决策 Decision

2026-05-30 经用户四问(AskUserQuestion)拍板,C5 推荐位规则:

1. **数量 3–5 个**:满 5 拒绝加入(复用预留 `BannerLimitExceeded` → 409);已配齐后移除到剩 3、再移除则拒绝(新增 `BannerBelowMinimumError` → 409);从空库爬坡允许 0–2 的「未配齐」中间态,后台醒目提示「需配满 3–5」。
2. **排序 = 上移/下移**(沿用 C3,**不做拖拽**,不引前端库)。
3. **挑选交互 = 即时增删**:商品列表每行「加入 Banner」按钮 + 推荐位区「移出 / 上移 / 下移」;已在推荐位不可重复加。
4. **下架联动**:商品被软下架 → 自动移出推荐位(被动触发,可致临时 <3 → 未配齐提示态)。
5. **锚点 F4a 修订**:「4 张」→「**3–5 张(典型 4)**」;§1 车机端措辞「4 张」同步改;修订 ADR-0004 幻灯张数。

## 理由 Rationale

- 首页 Banner 不能空、不能过少(<3 难看)、不能过多(>5);3–5 是运营美感区间,用户拍板。
- 即时增删贴合「商品列表旁加按钮」的交互直觉;穿梭框 / 草稿保存对 demo 过重。
- 上移/下移与 C3 一致、**零新依赖**(拖拽要引前端库,触 Rule 12 依赖门槛);demo 调序频率低,按钮够用。
- 下架自动移出 → 避免车机端 Banner 露出已下架商品(演示尴尬)。

## 替代方案 Alternatives Considered

- **数量**:A「最多 5、少了不限(0–5)」(原推荐,车机端兜底已支持)/ C「固定正好 4」(对齐旧 F4a,但每次须凑齐 4)。→ 用户选「必须 3–5」(B)。
- **排序**:真做拖拽(贴共识原话,但引前端库 + 破 C3 一致性)。→ 否。
- **挑选**:下拉框添加 / 左右穿梭框(一屏看全但前端偏重)。→ 否,选即时按钮。
- **下架**:① 自动踢出(选定)② 车机隐藏、后台保留可手动移除 ③ 不管照常显示。

## 后果 Consequences

- ✅ 推荐位规则清晰可测,3–5 区间明确;零新前端依赖,交互与分类统一。
- ⚠️ 「未配齐 <3」是合法中间态,车机端需 **≥3 才展示**(C8 实现门槛判断;US-CAR-01 空 / 单张场景降为防御性容错,保留不崩)。
- ⚠️ 新增 domain 异常 `BannerBelowMinimumError`(→ 409),[backend.md](../architecture/backend.md) HTTP 错误表在 C5 落地时补行。
- ⚠️ F4a 修订引发跨文档连锁,见下「豁免清单」。
